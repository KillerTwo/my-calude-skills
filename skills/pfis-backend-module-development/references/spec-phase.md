# 规格阶段

## 目标

先把前端 mock、页面行为和 api 约束沉淀为可执行的后端规格，再开始开发。

## 输入

- 用户指定的模块目录
- 前端页面代码
- 前端交互效果
- api 定义
- mock 数据或接口
- 接口数据类型和格式

## 输出目录

统一生成到 `docs/<module>/`。

## 必须生成的文档

### 1. `后端实施计划.md`

至少包含：

- 总目标
- 分阶段实施顺序
- 每阶段完成标准
- 与前端 mock 对齐的检查点

### 2. `后端开发任务清单.md`

必须拆成可独立提交的最小任务。每个任务至少写清：

- 任务编号
- 目标
- 输入依据
- 需要修改的后端层次
- 验收方式

### 3. `前端Mock接口Curl示例.md`

- 必须与前端 mock 一一对应
- 作为后续 smoke test 的直接依据

### 4. `前端mock对齐表.md`

必须逐项对齐：

- path
- method
- request
- response
- 字段名
- 字段类型
- 分页结构
- 状态值

### 5. `数据库表与状态流转设计.md`

- 只能写能被页面行为和 mock 直接支撑的设计
- 不能凭经验补字段
- 不能把不确定关系写成默认方案

## 规格生成硬规则

- 必须先生成规格文档，再开始后端开发。
- 规格文档必须先提交，再开始后端开发。
- 文档只能基于事实源生成。
- 关键结论必须可追溯。
- 无法直接推出的内容必须暂停确认。
- 真实后端路径以前端代码中的真实调用路径为准，禁止默认添加 `/api` 前缀。
- 分页接口如果前端 mock 与后端标准分页结构冲突，必须以 `PageResult` 为准，并在文档中显式标注为已知 mock 偏差。

## 规格审查要求

审查目标：

- 全部结论有事实来源
- 文档之间无冲突
- 足够支撑后端开发
- 与前端 mock 完全对齐

重点检查项：

- 是否存在无法证明来源的结论
- 实施计划和任务清单是否一致
- mock curl 和对齐表是否一致
- 对齐表与前端 api 定义是否一致
- 数据库设计是否超出了前端可证明范围
- 状态流转是否能被页面行为直接支撑

存在以下任一情况即审查不通过：

- 有猜测性结论
- 关键文档缺失
- mock 对齐不完整
- 状态流转无法证明
- 数据库核心关系无法证明

## 规格阶段完成定义

只有同时满足以下条件才算完成：

- 已由用户指定模块目录
- 已完整读取关键事实源
- 已生成模块规格文档目录
- 已生成全部 5 份规格文档
- 规格内不存在无法追溯来源的内容
- 已完成规格审查
