# Frontend Auto Code Generation

## Overview

Use this skill when a frontend page or dialog needs an automatically generated business code during create.

Preferred input includes:
- The page location
- The target field name
- The business type name

Typical inputs include:
- `给 src/views/material/device/index.vue 的 deviceCode 字段新增自动生成编号，业务类型名称为物料设备`
- `给设备管理弹框的 code 字段新增自动生成编号，业务类型名称为设备档案`

The goal is to:
- Read the target page code
- Follow the current page style
- Disable the input for the target field
- Generate a code only in create mode
- Write the code into the target field
- Release the generated code if the form is closed without saving

## When to Use

Use when:
- The user asks to auto-generate a business code in a frontend form
- The form is a create page, create dialog, or create-edit shared dialog
- The code must come from `generateCode`
- The generated code must be released if it was not used
- The field should be displayed but not manually editable

Do not use when:
- The field should remain user-editable
- The code is generated by the backend only after submit
- The task is unrelated to form create or dialog lifecycle

## Required Inputs

Before changing code, confirm these inputs from the user request or local code:
- Page location
- Target field name
- Business type name

If any of the three is missing, stop and ask for the missing input.

## Workflow

### 1. Read the page and determine the form mode

Inspect the target page and identify:
- The form model object
- The input component bound to the target field
- The create flow
- The edit flow
- The cancel, close, and reset flow

Common cases:
- Independent create page
- Create dialog only
- Shared create-edit dialog with mode flag such as `isEdit`, `formType`, `dialogMode`, or an existing record id

Required rule:
- If the page supports both create and edit, generate the code only during create
- Never overwrite the existing field value during edit

### 2. Import code-generation APIs using the correct local path

The required APIs are:

```ts
import { generateCode, releaseCode } from 'src/modules/api/material';
```

But the import path must not be copied blindly.

Required rule:
- Adjust the import path according to the actual page location and the project's alias or relative-path conventions
- Follow the import style already used by the target page
- If the page already imports from the same API module, merge the import instead of creating a duplicate import

### 3. Disable the target input

Find the input bound to the target field and make it disabled according to the page's existing component style.

Examples:

```vue
<el-input v-model="form.deviceCode" disabled />
```

or

```vue
<a-input v-model:value="form.deviceCode" :disabled="true" />
```

Required rule:
- Keep the UI component library style already used by the page
- Only disable the requested field
- Do not alter unrelated form controls

### 4. Generate code during create only

When the form enters create mode, call:

```ts
const res = await generateCode('业务类型名称');
```

Then write the generated value into the target field.

Typical pattern:

```ts
const res = await generateCode('物料设备');
generatedCode.value = res?.data || '';
form.deviceCode = generatedCode.value;
```

Required rule:
- Store the generated code in a dedicated variable such as `generatedCode`
- Set the field value from the generated code
- Generate only once per create open unless the page intentionally discards and reopens the form
- In a shared create-edit dialog, skip this logic entirely for edit mode

### 5. Preserve existing save logic

This skill performs additive changes.

Required rule:
- Do not rewrite the submit flow unless needed to integrate the generated field
- Do not delete existing validation, submit, or close logic
- Only add the minimum code needed to support generation and release

If the page already has create initialization logic:
- Append the code-generation call into the existing create branch
- Do not replace unrelated initialization code

### 6. Release unused code on cancel or close

If the form is cancelled, closed, or dismissed without saving:
- Call `resetForm()` to clear form fields
- Release the generated code

Required pattern:

```ts
resetForm();
releaseCode(generatedCode.value).catch(() => {});
generatedCode.value = '';
```

Rules:
- Release only when a generated code exists and it has not been successfully saved
- Hook this into the actual cancel or close path used by the page
- In dialog components, also cover the close behavior triggered by the dialog itself if that can bypass the cancel button

### 7. Avoid releasing after successful save

If the form was successfully saved:
- Do not release the code
- Clear the temporary generated-code state only after the save lifecycle is complete if needed by page style

Required rule:
- Distinguish clearly between "closed without saving" and "saved successfully"
- A successful save consumes the generated code

### 8. Final verification

Before finishing, verify:
- The correct page was updated
- The target input field is disabled
- The code-generation import path matches the page's actual import style
- The code is generated only in create mode
- Edit mode does not request a new code or overwrite an existing value
- The generated value is written to the correct field
- Existing submit and validation logic were preserved
- Cancel or close without saving calls `resetForm()`
- Cancel or close without saving releases the unused code
- Successful save does not release the code

## Output Standard

When applying this pattern, make changes in this order:
1. Read the page and identify create/edit/reset lifecycle
2. Add or merge the correct API imports
3. Disable the target input field
4. Add create-only code generation logic
5. Add unused-code release logic to cancel or close flows
6. Re-check create/edit branching and form cleanup behavior

## Shared Dialog Rule

If the page uses one dialog for both create and edit:
- Generate the code only when opening create mode
- Do not generate or replace the code when opening edit mode
- Preserve any existing edit data loading logic

Typical expectation:
- Open create dialog -> generate code -> fill field -> disable field
- Open edit dialog -> keep existing field value -> do not call `generateCode`

## Common Mistakes

- Hardcoding the import path without adapting it to the page
- Generating the code in both create and edit mode
- Forgetting to disable the target input
- Writing the generated value to the wrong form field
- Releasing the code after a successful save
- Forgetting to release the code when the dialog closes directly
- Replacing existing reset or submit logic instead of extending it
- Creating duplicate imports for the same API module

## Default Pattern

Use this decision rule:
- Pure create page or create dialog: generate code on initialization
- Shared create-edit dialog: generate code only in the create branch
- Cancel or close without saving: `resetForm()` and `releaseCode(generatedCode.value).catch(() => {})`

Always follow the page's existing code style, lifecycle structure, and import conventions.
